## 2. 目的

本標準は、アイ・ツーが構築する10種類のAI社員について、開発方法、設計書、レビュー、テスト、GitHub管理、運用ルールを統一することを目的とする。

個別のAIをバラバラに開発するのではなく、共通の開発手順と共通基盤を使用し、継続的に改善・追加できる仕組みとして構築する。

---

## 3. プロジェクトの基本方針

本プロジェクトでは、オールAI化企業を次のように定義する。

> 人が仕事を探す会社から、AIが仕事を見つけ、人が判断する会社へ。

AIは、社員を置き換えることを目的としない。

AIには、次のような定型的・反復的な仕事を担当させる。

- 情報検索
- 情報整理
- 転記
- 分類
- 集計
- 期限確認
- 催促
- 議事録作成
- 定型文作成
- 対応案の提示
- 異常や機会の発見

人は、次の仕事を担当する。

- 最終判断
- 承認
- 顧客との関係構築
- 提案
- 交渉
- 例外対応
- 現場判断
- 教育
- 改善
- 最終責任

## 4. 対象となるAI社員

本プロジェクトでは、次の10種類のAI社員を構築する。

| No. | AI社員 | 主な役割 |
|---:|---|---|
| 1 | AI会議秘書 | 会議準備、録音・記録、議事録、決定事項、タスク作成 |
| 2 | 総務AI | 社内規程、手順、申請方法、社内問い合わせへの回答 |
| 3 | 顧客AI | 顧客情報、担当者、契約、案件、対応履歴の整理 |
| 4 | メール受付AI | メール分類、顧客特定、返信案、担当者へのタスク発行 |
| 5 | 見積AI | 過去見積検索、見積ドラフト作成、原価・利益率確認 |
| 6 | 保守AI | 障害履歴検索、原因候補、確認項目、対応手順の提示 |
| 7 | 営業AI | 追客対象、契約更新、追加提案候補、営業機会の発見 |
| 8 | 契約AI | 契約内容、更新期限、解約条件、更新案内の管理 |
| 9 | 経理AI | 請求、入金、未収、支払、異常取引の監視 |
| 10 | 経営AI | 売上、利益、工数、リスク、機会、要判断事項の整理 |

## 5. プロトタイプ開発方針

2026年9月中旬のデモでは、10種類のAI社員すべてについて、最低1つの業務シナリオが動く状態を目標とする。

すべての機能を完成させるのではなく、次の状態をプロトタイプ完成とする。

1. 利用者がWeb画面またはチャット画面から指示できる
2. AIが必要な情報を取得できる
3. AIが回答案または処理案を作成できる
4. 必要に応じてn8nが処理を実行できる
5. 結果を画面またはNotionで確認できる
6. 人が内容を確認し、承認できる

各AI社員について、デモ用の代表シナリオを1つ以上用意する。

## 6. 標準技術構成

### 6.1 基本構成

| 区分 | 標準技術 |
|---|---|
| フロントエンド | Next.js、React、TypeScript |
| バックエンド | Python、FastAPI |
| AI | ChatGPT、OpenAI API |
| ワークフロー自動化 | n8n |
| プロトタイプDB | Notionデータベース |
| 本格運用DB候補 | PostgreSQL |
| ソース・設計書管理 | GitHub |
| 開発支援 | ChatGPT、Codex |
| 実行環境 | Webブラウザを基本とする |
| 将来対応 | スマートフォン、タブレット、外部システム連携 |

### 6.2 技術選択の原則

- 最初は、動くプロトタイプを優先する
- データは当面Notionに保存する
- 複雑な自動処理はn8nで構築する
- 画面はWebブラウザで利用できるようにする
- スマートフォンでも閲覧できるレスポンシブ設計とする
- 利用者やデータ量が増えた場合は、PostgreSQLなどの専用DBへ移行する
- AIモデルや外部サービスは、後から交換できる構造とする

10. GitHub運用ルール
10.1 基本ルール
設計書とプログラムはGitHubで一元管理する
チャットの中だけに重要な仕様を残さない
ChatGPTで整理した内容は、必ずMarkdownファイルに反映する
変更した理由が分かる単位でコミットする
一度に複数の無関係な変更をコミットしない
パスワード、APIキー、個人情報は登録しない
10.2 コミットするタイミング
要件定義を作成したとき
設計書を変更したとき
機能を追加したとき
不具合を修正したとき
テストを完了したとき
プロトタイプ版を公開するとき
10.3 コミットメッセージの例
docs: AI会議秘書の要件定義を追加
docs: 開発標準のレビュー手順を修正
feat: 会議議事録の生成機能を追加

11. レビュー・承認ルール
11.1 レビュー体制
対象	一次レビュー	最終確認・承認
構想	ChatGPTによる論点整理	プロジェクト責任者
要件定義	ChatGPTによる要件漏れ確認	プロジェクト責任者
基本設計	ChatGPTによる構成確認	プロジェクト責任者
詳細設計	ChatGPTによる整合性確認	実装担当者・責任者
ソースコード	Codexによるコードレビュー	人による最終確認
テスト結果	AIによる不足確認	利用者・責任者
デモ公開	社内利用者による操作評価	プロジェクト責任者

11.2 レビューの原則
AIだけで承認を完了させない
最終判断は必ず人が行う
仕様変更の理由を記録する
未解決事項は課題としてGitHubに残す
重大な問題が残っている場合は次のフェーズへ進まない
プロトタイプでは、残課題を明示したうえで次へ進むことができる

11.3 最終承認者
プロジェクト全体およびプロトタイプ公開の最終承認者は、プロジェクト責任者である松崎秀規とする。

### 11.4 レビュー記録の作成

構想、要件定義、設計、実装、テスト、デモ公開の各段階で、レビューを実施した場合は、その結果を記録する。

レビュー記録は、単に「確認済み」と残すだけではなく、次の内容が分かる状態にする。

- 何をレビューしたか
- 誰がレビューしたか
- いつレビューしたか
- どのような指摘があったか
- 指摘に対してどのように対応したか
- 未対応事項が残っているか
- 次のフェーズへ進んでよいか

レビュー記録は、各AI社員のフォルダ内に保存する。

保存例：

```text
docs/
└── ai-employees/
    └── 01-meeting-ai/
        ├── 要件定義.md
        ├── 基本設計.md
        ├── 詳細設計.md
        ├── テスト仕様.md
        └── レビュー記録.md

11.5 レビュー実施のタイミング

次のタイミングでレビューを実施する。

タイミング	レビュー対象	確認内容
構想完了時	構想書	目的、対象業務、期待効果が明確か
要件定義完了時	要件定義書	利用者、機能、入力、出力、制約に漏れがないか
基本設計完了時	基本設計書	全体構成、データ、画面、処理の流れが整合しているか
詳細設計完了時	詳細設計書	Notion、n8n、API、プロンプトの仕様が実装可能か
実装完了時	ソースコード・n8n	設計どおりに実装されているか
テスト完了時	テスト結果	重大な不具合や未確認項目が残っていないか
デモ前	プロトタイプ全体	一連の業務シナリオが正常に動くか
改善後	修正版	指摘事項が正しく反映されているか

11.6 レビュー結果の判定

レビュー結果は、次の3段階で記録する。

判定	意味
承認	問題なく、次のフェーズへ進める
条件付き承認	軽微な課題はあるが、対応期限を決めて次へ進める
差し戻し	重大な課題があり、修正と再レビューが必要

「条件付き承認」とする場合は、未対応事項、担当者、期限を必ず記載する。

「差し戻し」とする場合は、差し戻し理由と再レビュー予定を記載する。

11.8 レビュー記録の運用ルール
レビューを実施した当日中に記録する
指摘事項は、口頭やチャットだけで終わらせない
指摘事項ごとに担当者と期限を設定する
対応完了後は、対応者以外が確認する
重大な指摘は、対応完了まで「完了」としない
未対応事項を残したままデモを行う場合は、既知の課題として明示する
同じ指摘が繰り返された場合は、開発標準やテンプレート自体を改善する
レビュー記録の変更履歴はGitHubのコミットで残す

11.9 AIによるレビューの注意事項

ChatGPTやCodexによるレビューは、人のレビューを補助する目的で使用する。

AIによるレビューでは、主に次の点を確認する。

要件の漏れ
設計書間の矛盾
曖昧な表現
例外処理の不足
セキュリティ上の懸念
テスト項目の不足
コード上の不具合候補
改善案

ただし、AIのレビュー結果だけで承認してはならない。

顧客対応、金額、契約、個人情報、外部送信、経営判断に関する事項は、必ず人が最終確認する。

13. n8n開発ルール
n8nは、システム間のデータ連携と自動処理に使用する
1つのワークフローに過度な機能を詰め込まない
ワークフロー名に対象AIと処理内容を含める
エラー発生時の通知先を設定する
実行結果を確認できるログを残す
外部送信やデータ更新の前に、必要に応じて人の承認を入れる
n8nのワークフローはJSON形式でGitHubに保存する

ワークフロー名の例：

meeting-ai_create-minutes
meeting-ai_create-tasks
mail-ai_classify-message
estimate-ai_create-draft
accounting-ai_check-payment

14.2 移行判断

次の状態が発生した場合は、専用データベースへの移行を検討する。

データ件数が増加し、表示や検索が遅くなった
複雑な集計が必要になった
複数システムとのリアルタイム連携が必要になった
詳細な権限管理が必要になった
監査ログが必要になった
Notionの利用料金または制約が運用上の問題になった

移行先の第一候補はPostgreSQLとする。

15. テスト基準
15.1 共通テスト項目

各AI社員について、最低限次のテストを行う。

正常な入力で回答できる
入力不足の場合に確認質問ができる
誤った形式の入力を処理できる
Notionから必要な情報を取得できる
Notionへ結果を登録できる
n8nワークフローが正常終了する
エラー発生時に内容を確認できる
AIの回答内容を人が確認できる
承認前に外部送信されない
同じ操作を繰り返しても重大な問題が発生しない
15.2 テストデータ
原則として架空の顧客・案件データを使用する
実データを使用する場合は、必要最小限とする
個人情報や機密情報が画面、ログ、GitHubに残らないことを確認する
